### 2.2 현재 판정 범위

- 최종 서비스 판정 범위는 `fall`과 `normal`이다.
- `standing`, `sitting`, `walking`, `lying`, `fall_down`은 내부 진단 상태이며 외부 최종 행동 정확도 주장에 사용하지 않는다.
- `lying`은 화면에서 숨길 수 있어도 내부 hard-negative와 오류 분석 상태로 유지한다. `lying`만으로 낙상 확정 알림을 발생시키지 않는다.
- `video/validation`에서 확인된 외부 정답 범위는 `fall/normal`이다. 행동별 정답이 없는 상태에서 standing/sitting/walking/lying confusion matrix를 만들거나 성능을 주장하지 않는다.

### 2.3 현재 장치 안전 경계

- Pi와 Orin은 마지막 확인에서 SSH 연결 가능했다. 이후 상태는 재개 시 read-only로 다시 확인한다.
- Orin은 shadow-only 상태를 유지해야 한다. 일반 service enable, production cutover, alert activation은 금지한다.
- Pi runtime은 `BACKEND_URL/EC2_STREAM_HOST`에 의해 external RTSP `rtsp://54.116.119.98:8554/P001`로 publish한다. viewer 경로와 end-to-end 지연을 확인하기 전 localhost publish로 변경하지 않는다.
- 마지막 캡처 장면은 벽이었고 사람·침대·바닥·의자가 식별되지 않았다. 이 장면의 `candidate_count=0`, pose confidence `0.0`은 사람 검출 품질 증거가 아니다.
- Pi의 원격 `main.py`는 재시작 오류 발생 전 백업으로 복구된 상태다. 로컬 `device_transfer/camera/edge/main.py`는 Pi에 없는 `tools.roi_bootstrap` 의존성이 있을 수 있으므로 비교 없이 재배포하지 않는다.

### 2.4 모델과 ROI 경계

- 현재 YOLO, XGBoost, MultiTask ST-GCN 모델을 재학습·튜닝·교체하지 않는다.
- SAM3 checkpoint/cache는 확보되지 않았다. SAM3가 설치·실행됐다고 주장하지 않는다.
- 수동 Flask ROI 도구는 실제 방 첫 화면에서 `bed`, `floor`, `chair` polygon을 사람이 입력하는 fallback이다.
- 실제 방 frame과 사용자 입력 없이 ROI 좌표를 생성하지 않는다. ROI가 없으면 `roi_unknown` 또는 `pending_review`로 fail-closed 처리한다.
- validation 영상에서 운영실 전용 ROI를 추정해 장치에 배치하지 않는다.

## 3. 미완료 작업

### 3.1 실제 사람 skeleton jump와 화면 멈춤 검증

상태: `DEPLOYED_TELEMETRY_PASS` (2026-07-23 18:45 KST)

- 현재 WebRTC 화면에 실제 사람이 확인됐다. 하지만 Pi에 배포된 streamer는 동일 track ID의 새 pose 결과도 이전 geometry를 optical flow로 대체하거나 실패 시 hold할 수 있어, 사람 형태와 분리된 skeleton이 관측됐다.
- 로컬 수정안은 새 pose 결과를 즉시 원본 YOLO geometry로 그리도록 하고, 새 결과 사이의 짧은 공백에서만 기존 motion compensation을 사용한다. 모델, YOLO 설정, confidence threshold, tracker 설정은 변경하지 않는다.
- 사용자가 카메라 테스트 대신 영상 테스트를 지시했다. 동일 Pi config와 `yolo26n-pose-320` ONNX를 PC에서 사용하되, RTSP transport/FFmpeg/camera는 시작하지 않는다.
- `FD_0037` 첫 30프레임(640x360)에서는 30/30프레임, 30 detections, raw YOLO geometry와 fresh streamer geometry mismatch 0건이다. 저장된 시작/끝 출력 프레임의 bbox/skeleton은 사람 형상에 맞는다.
- `FD_0037` 10초의 누운 사람 30프레임과 `FD_0038` 10초의 구부린 사람 30프레임은 각각 0/30 pose detection이다. 이 결과는 renderer 고정이 아니라 현행 `yolo26n-pose-320`의 저자세 사람 미검출 근거다. 모델/설정은 변경하지 않았다.
- fresh-pose streamer patch는 `test_rtsp_streamer.py` 17/17, 새 video replay helper test 2/2, `py_compile`을 통과했다. Pi SSH 복구 후 2026-07-23 18:34 KST에 원격 원본을 백업하고 `main.py`와 `rtsp_streamer.py`의 fresh-pose patch만 배포했다. Pi 서비스는 `active`, `NRestarts=0`이며, remote `py_compile`과 source 확인도 통과했다.
- 현장 카메라 visual QA는 사용자 지시에 따라 수행하지 않았다. 배포된 fresh-pose 경로의 기하 정합성 근거는 PC 영상 리플레이이며, 저자세 미검출 문제는 별도 근거로 유지한다.
- 비동기 경로 검토에서 pose result는 원본 capture packet을 context로 보존하지만, streamer는 같은 loop의 최신 capture frame을 사용한다는 점을 확인했다. `FD_0037` 30프레임의 raw bbox center 비교에서는 1~3 frame lag가 원본 3840x2160에서 최대 `11.715px`, 640x360 환산 최대 `1.953px`였다. 이 샘플에서 큰 기하 이탈을 재현하지 못했으므로, 근거 없이 stream-frame 선택 방식을 바꾸지 않는다.
- Pi 배포 후 최신 30.0194초 telemetry는 capture `30.0139 FPS`, target `30.0 FPS`, dropped estimate `0`, inference `23.5847 FPS`, pose p95 `44.5477 ms`, loop p95 `40.4903 ms`다. 이 값은 stream continuity와 process health 근거이며, 해당 window의 `avg_pose_confidence=0.0`이므로 사람 자세 정확도 근거로 사용하지 않는다.

### 3.1a Pi Skeleton WebSocket 동기 flush 분리 검토

상태: `PENDING_USER_APPROVAL` (2026-07-23 05:24 KST)

- 확인된 근거: Pi `main.py`는 `flush_interval_sec=1.0`마다 메인 루프에서 `SkeletonWebSocketSender.send_batch_sync()`를 호출한다. 이 호출은 `asyncio.run()`으로 새 event loop를 만들고, WebSocket 연결·한 배치 전송·연결 종료를 동기적으로 수행한다. Orin 로그의 약 1초 `connection open/closed` 반복은 이 구현과 일치한다.
- 현재 당일 Pi 성능 행은 capture 약 `30 FPS`, loop p95 약 `40 ms`, inference 약 `23 FPS`, drop `0`이다. 따라서 현재 수치만으로 3초 정지가 Pi 메인 루프에서 재현됐다고 단정할 수는 없다. 다만 전송 지연 또는 pending batch 재전송 시 메인 루프가 최대 `request_timeout_sec=10`초와 재시도 backoff만큼 멈출 위험은 남는다.
- 방안 A (권장): 기존 WebSocket payload와 Orin endpoint는 유지하고, Pi에 최신 Skeleton batch 한 개만 보관하는 단일 송신 워커를 둔다. 메인 루프는 새 batch로 교체만 하고 즉시 반환하며, 워커만 기존 bounded retry를 수행한다. 네트워크가 느려도 RTSP/YOLO 루프를 막지 않는 것이 목적이다.
- 방안 B (보류): sender가 장기 asyncio connection을 소유하고 재연결하는 persistent WebSocket으로 변경한다. handshake 부하는 줄지만 lifecycle, shutdown, reconnect와 pending-file 동시성 설계가 추가되어 범위가 더 크다.
- 방안 C (제외): Skeleton WebSocket을 끈다. 화면 송출 부담은 줄 수 있으나 Orin shadow 분석 입력이 끊기므로 사용하지 않는다.
- 승인 전에는 sender 동작, WebSocket contract, Pi/Orin 서비스 설정을 바꾸지 않는다. 승인 시 A만 구현하고, 30~60분 및 24시간 soak는 수행하지 않는다.
