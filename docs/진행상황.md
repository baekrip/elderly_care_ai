### 2.2 목표 구조: 실장비 구성 (2026-05-14 확정)

```text
[카메라1] Raspberry Pi 5 + wide v3 카메라
    → 경량 YOLO pose ONNX (skeleton/bbox/행동속도/features 추출)
    → RAM 링 버퍼 (위험 clip 임시 보관)
    → RTSP H.264 스트리밍 (MediaMTX + FFmpeg, 프론트엔드/미디어 서버용)
    → WebSocket skeleton/행동속도 JSON → Orin Nano로 전송
    → Orin REST clip request 수신 후 Face blur clip 전송

[엣지] Jetson Orin Nano (8GB)
    → Pi5 skeleton WebSocket 수신
    → XGBoost (1차 행동 분류)
    → sliding window + Event Queue/FSM + smoothing
    → ST-GCN + TensorRT FP16 → 위험 정밀 판정
    → 위험 timestamp 기준 Pi5에 clip_start_ms/clip_end_ms REST 요청
    → POST /api/v1/events/batch 또는 WebSocket → 서버/미디어 서버 DB
    → POST /api/v1/alerts/immediate → 위험 시만
    → clip metadata/file 업로드 → 서버/미디어 서버 DB 또는 S3

서버 (백엔드 + 미디어 서버 + DB + 2차 분류 AI + 프론트엔드)
    → Backend API (events/batch, alerts/immediate, clips/upload)
    → Media server/DB (RTSP/WebRTC 변환, clip metadata, 실시간 화면 제공)
    → 2차 분류 AI (생활 패턴/장기 위험 분석)
    → 프론트엔드 (실시간 화면, 타임라인, 알림, 위험 clip 조회)
```

> **Pi5 YOLO 구동 방식**: `P5-B`로 먼저 진행. Hailo AI HAT(P5-A)는 Pi5 FPS 또는 skeleton 품질이 부족할 때 재검토.
> **Orin Nano 부하 예상**: Pi5 skeleton 수신 + XGBoost + ST-GCN + TensorRT FP16 + clip 요청/전송 + 서버 연동 동시 구동은 실기기 벤치마크 필요.
> **Pi5 YOLO 주의**: P5-B는 CPU 기반 ONNX 경량화이므로 30초 평균 FPS, pose confidence, WebSocket 전송 지연/누락을 반드시 같이 기록.


### 2.3 데이터 흐름 (capture_ts / analysis_ts 분리 기준)

```text
[프레임 캡처]  → capture_ts 기록
      ↓
[YOLO 추론]    → skeleton / bbox
      ↓
[Pi5인 경우]   → WebSocket skeleton/행동속도 feature JSON으로 Orin 전송
      ↓
[Orin feature/window] → 5초 skeleton window, motion feature, smoothing score
      ↓
[XGBoost 분류] → action_label, xgboost_tier_ms 기록
      ↓
[TriggerEngine/FSM] → candidate/event 상태 생성
      ↓
[ST-GCN 추론] → stgcn_label, stgcn_inference_ms, analysis_ts 기록
      ↓
[위험 확정]   → Orin이 위험 timestamp 기준 clip_start_ms/clip_end_ms로 Pi5에 REST 요청, Pi5가 Face blur 처리
      ↓
[서버]        → WebSocket/REST로 분석 결과와 clip metadata를 서버/미디어 서버 DB에 전송
               POST /api/v1/events/batch (ABNORMAL/DANGER, capture_ts = ts 기준)
               POST /api/v1/alerts/immediate (위험 시만)
```

## 7. 현재 관찰된 한계

### 7.1 ST-GCN synthetic fall 오분류

- synthetic fall payload → NORMAL 분류된 케이스가 있었다
- validation 기준 97.46%이지만 실제 window 기준 보정 필요
- 실제 낙상 replay → 좌표 정규화 대조 → class weight/focal loss 순서로 보정 필요

### 7.2 candidate 발생률 실검증 미완

- gradual fall trigger와 threshold 완화는 구현됨
- 실제 `abnormal_drop` replay에서 candidate 발생률을 아직 다시 측정하지 않았다
- 정상 구간 오탐도 함께 재확인해야 한다

### 7.3 clip_json 실제 채움 미검증

- candidate → ST-GCN → clip_json 전체 경로가 자동으로 채워지는지 미검증
- clip_start_ms, clip_end_ms 기반 clip 요청은 구현됨
- 실제 낙상 candidate가 생성되어야 검증 가능

### 7.4 외부 전송 실연동 미검증

- candidate 결과 기반 ABNORMAL/DANGER 외부 전송은 구현됨
- `backend_pending.jsonl` 실패 저장/재전송도 구현됨
- 10초 batch scheduler 구현됨
- 남은 것은 Orin 실기기에서 외부 백엔드 수신까지 확인하는 것

### 7.5 Pi5/Orin 실기기 성능 미검증

- Pi5 ONNX Runtime 분기는 구현됐지만 실제 `.onnx` 모델 파일과 Pi5 FPS는 미검증
- Orin에서 Pi5 skeleton 수신 + Orin camera2 YOLO + XGBoost + ST-GCN + RTSP + clip buffer 동시 구동 FPS/지연도 미검증
- `perf_stats.jsonl`과 Orin skeleton 수신 로그 기준으로 FPS, pose confidence, WebSocket 지연, candidate rate를 측정해야 한다

### 7.6 RTSP 실제 송출 검증 미완

- `edge/rtsp_streamer.py`는 command wrapper 상태
- `edge/config.raspi_cam01.yaml`, `edge/config.orin_cam02.yaml`에 FFmpeg→MediaMTX command template 작성 완료
- 남은 것은 MediaMTX 실행, `/dev/video*` 번호, edge inference와 FFmpeg 동시 접근 여부 검증

### 7.7 clip upload 운영 API 미확정

- backend JSON pending과 별개로 clip upload 실패 pending 기록은 구현됨
- 운영 백엔드의 clip upload endpoint 또는 presigned URL 방식 확정 후 실제 재전송 자동화 여부를 결정한다

### 7.8 ST-GCN MP4 직접 재분석 미구현

- 현재 ST-GCN은 skeleton JSON sequence 기준으로 동작한다
- T-C 확장 시 clip 영상에서 YOLO 재추론 후 ST-GCN sequence를 다시 만드는 경로가 필요하다
