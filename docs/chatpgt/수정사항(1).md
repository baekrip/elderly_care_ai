```text

5. 자동 전송 파이프라인은 아직 완전히 동작하지 않음.
6. 스트리밍은 connection open → closed 반복으로 아직 프론트까지 표시되지 않음.
7. 파일 전송과 스트리밍은 백엔드 events/batch 전송과 별도 흐름이므로 분리해서 수정 필요함.
```

## 3. 처음 발생한 주요 문제: 엣지에서 백엔드 연결 timeout

### 증상

엣지 또는 기기에서 백엔드로 다음 요청 시 timeout 발생:

```bash
curl -v http://43.201.18.127:8000/health
```

오류 예시:

```text
Trying 43.201.18.127:8000...
connect to 43.201.18.127 port 8000 failed: 연결 시간 초과
curl: (28) Failed to connect
```

### 원인

처음에는 백엔드 포트를 `8000`으로 잘못 보고 있었음. 실제 백엔드는 `5000` 포트에서 동작 중이었다.

잘못된 주소:

```text
http://43.201.18.127:8000
```

또는 이후 IP 변경 전 주소:

```text
http://43.201.18.127:8000
```

정상 확인된 현재 백엔드 주소:

```text
http://54.116.119.98:5000
```

### 해결 작업

백엔드 요청 포트를 `5000`으로 수정 후 `curl` 연결 성공 확인.

정상 테스트 명령:

```bash
curl -v http://54.116.119.98:5000/health
```

## 4. PowerShell curl 이슈

### 증상

Windows PowerShell에서 다음 명령 실행 시 오류 발생:

```powershell
curl 43.201.18.127/health
```

오류:

```text
curl : 원격 서버에 연결할 수 없습니다.
```

### 원인

PowerShell의 `curl`은 실제 curl이 아니라 `Invoke-WebRequest` alias일 수 있음. 또한 URL에 `http://`와 포트가 빠져 있었음.

```powershell

```

Linux/엣지에서는:

```bash
curl -v http://54.116.119.98:5000/health
```

## 5. 백엔드 403 Invalid token 문제

### 증상

다음 요청에서 403 발생:

```bash
curl -v -X POST http://54.116.119.98:5000/api/v1/events/batch \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"events":[]}'
```

오류 예시:

```text
HTTP/1.1 403 FORBIDDEN
<p>Invalid token</p>
```

### 확인한 사실

헤더 형식 자체는 백엔드 요구사항과 일치함.

백엔드가 요구하는 형태:

```python
headers = {
    "Authorization": f"Bearer {APP_TOKEN}",
    "Content-Type": "application/json",
}
requests.post(url, headers=headers, json=payload)
```

curl에서 같은 의미:

```bash
-H "Authorization: Bearer <TOKEN>"
-H "Content-Type: application/json"
```

### 원인 후보였던 것

1. `.env` 형식 오류 가능성

잘못된 예:

```env
APP_TOKEN:app_token
```

정상:

```env
APP_TOKEN=app_token
```

2. 백엔드 런타임의 `APP_TOKEN`과 엣지 config의 `backend.token` 불일치
3. 백엔드 재시작 미반영
4. 코드가 `APP_TOKEN`이 아닌 다른 환경변수를 보고 있을 가능성
5. 토큰 앞뒤 공백/개행/따옴표 포함 가능성

### 현재 해결 상태

엣지 config 값을 그대로 읽어 단일 JSON을 전송하는 Python 테스트에서 성공 확인됨.

성공 로그:

```text
[TEST] url = http://54.116.119.98:5000/api/v1/events/batch
[TEST] token_len = 32
[TEST] token_head = '7752b2'
[TEST] token_tail = '0467cd'
[RESULT] status = 201
[RESULT] body = {"count":1,"results":[{"event_id":18,"stored":true}]}
```

의미:

```text
엣지 → 백엔드 연결 정상
토큰 정상
/api/v1/events/batch 경로 정상
JSON 스키마 정상
백엔드 DB 저장 정상
```

보안상 실제 토큰 원문은 문서에 기록하지 않음.

## 6. 백엔드 base_url 문제

### 문제 발견

`server/config.orin.yaml`에 다음처럼 되어 있었음:

```yaml

  enabled: true
  base_url: "54.116.119.98:5000"
```

### 원인

`server/services/backend_forwarder.py`의 `_post_json()` 함수에 다음 검사가 있음:

```python
if not url.startswith(("http://", "https://")):
```

```yaml

  enabled: true
  base_url: "http://54.116.119.98:5000"
```

최종적으로 필요한 형태:

```yaml
backend:
  enabled: true
  base_url: "http://54.116.119.98:5000"
  device_key: "pi5-home001-cam1"
  token: "<BACKEND_APP_TOKEN>"
```

## 8. SQLite database is locked 문제

### 증상

엣지 로그에서 반복 발생:

```text
sqlite3.OperationalError: database is locked
sqlalchemy.exc.OperationalError: database is locked
```

발생 위치:

```text
server/api/skeleton_ws.py
→ persist_pi5_skeleton_batch()
→ _ensure_camera()
→ session.get(CameraRecord, frame.camera_id)
→ autoflush
→ INSERT INTO activity_frames
→ database is locked
```

동반 증상:

```text
WebSocket /ws/skeleton/raspi_cam01 [accepted]
connection open
connection closed
```

### 원인

SQLite는 동시 write에 약함. PI5 skeleton frame이 계속 들어오면서 `activity_frames` INSERT가 빈번하게 발생했고, 동시 DB 접근 또는 autoflush 타이밍 문제로 lock 발생.

### 수행한 조치

DB 경로 확인:

```text
server/storage/orin_local_server.db
```

WAL 모드 적용:

```bash
sqlite3 server/storage/orin_local_server.db "PRAGMA journal_mode=WAL;"
```

무결성 확인:

```bash
sqlite3 server/storage/orin_local_server.db "PRAGMA integrity_check;"
```

확인 결과:

```text
ok
```

WAL checkpoint:

```bash
sqlite3 server/storage/orin_local_server.db "PRAGMA wal_checkpoint(TRUNCATE);"
```

`server/config.orin.yaml` DB URL에 timeout 추가 필요:

```yaml
url: "sqlite+aiosqlite:///server/storage/orin_local_server.db?timeout=30"
```

### 주의 사항

`PRAGMA synchronous;` 결과가 `2`로 나왔음.

의미:

```text
2 = FULL
1 = NORMAL
```

`PRAGMA synchronous=NORMAL`은 연결 세션 단위 설정일 수 있으므로, 서버 코드에서 연결마다 PRAGMA 적용하는 것이 더 안전함.

권장 코드:

```python
from sqlalchemy import event

@event.listens_for(engine.sync_engine, "connect")
def set_sqlite_pragma(dbapi_connection, connection_record):
    cursor = dbapi_connection.cursor()
    cursor.execute("PRAGMA journal_mode=WAL;")
    cursor.execute("PRAGMA synchronous=NORMAL;")
    cursor.execute("PRAGMA busy_timeout=30000;")
    cursor.close()
```

## 10. WebSocket open/closed 반복 문제

### 증상

엣지 로그에 반복 출력:

```text
INFO:     192.168.45.29:xxxxx - "WebSocket /ws/skeleton/raspi_cam01" [accepted]
INFO:     connection open
INFO:     connection closed
```

### 의미

`192.168.45.29`는 PI5일 가능성이 높음. PI5가 엣지 `/ws/skeleton/raspi_cam01`에 연결했다가 바로 끊고 재접속하는 상태.

### 가능한 원인

1. PI5 WebSocket 클라이언트가 프레임마다 `connect → send → close` 구조로 되어 있음
2. 서버가 DB 저장 중 예외 발생으로 WebSocket을 닫음
3. skeleton 수신 함수가 내부 예외를 처리하지 않고 ASGI 예외로 터짐
4. 프론트가 붙는 WebSocket과 PI5가 보내는 WebSocket endpoint가 분리되어 있지 않음

### 확인 명령어

```bash
tail -n 300 logs/orin_server.log | grep -E "WebSocket|connection open|connection closed|Traceback|Exception|ERROR|database is locked"
```

PI5 쪽 프로세스 확인:

```bash
ps aux | grep -i "python\|skeleton\|websocket\|raspi"
```

### 해결 방향

PI5 클라이언트는 다음처럼 지속 연결 구조여야 함.

잘못된 구조:

```python
async with websockets.connect(url) as ws:
    await ws.send(data)
```

정상 구조:

```python
async with websockets.connect(url) as ws:
    while True:
        await ws.send(data)
        await asyncio.sleep(0.03)
```

서버 측에서는 DB 저장 실패가 WebSocket을 죽이지 않도록 `try/except` 처리 필요.

## 11. 스트리밍이 프론트까지 안 가는 문제

### 현재 상태

```text
PI5 → 엣지 연결은 들어옴
그러나 connection open → closed 반복
프론트 스트리밍 표시 안 됨
```

### 확인해야 할 구간

```text
1. PI5 → 엣지 WebSocket 수신
2. 엣지 skeleton_ws.py 내부 처리
3. 엣지 → 프론트 WebSocket broadcast
4. 프론트 WebSocket URL 및 렌더링
```

### WebSocket endpoint 확인 명령어

```bash
grep -R "@.*websocket\|websocket(\"/ws\|/ws/" -n server
```

### skeleton_ws.py에서 프론트 송출 코드 확인

```bash
grep -n "send_json\|send_text\|broadcast\|frontend\|dashboard\|client\|persist_pi5" server/api/skeleton_ws.py
```

### 판단 기준

`skeleton_ws.py`에 `persist_pi5_skeleton_batch()`만 있고 `send_json`, `broadcast`, `frontend_clients` 같은 코드가 없다면:

```text
PI5 skeleton 수신 후 DB 저장만 하고, 프론트로 실시간 송출하지 않는 구조
```

이 경우 스트리밍이 프론트까지 안 가는 것은 정상이며, 프론트용 WebSocket endpoint와 broadcast 로직 추가가 필요함.

### 프론트 WebSocket URL 확인

프론트 프로젝트 폴더에서:

```bash
grep -R "new WebSocket\|ws://\|wss://\|EventSource" -n . 2>/dev/null | head -100
```

주의:

```js
ws://localhost:8000/...
```

브라우저에서 `localhost`는 엣지가 아니라 프론트 실행 PC 자신임.

엣지 IP 확인:

```bash
hostname -I
```

정상 예:

```js
ws://192.168.45.241:8000/<실제_WS_경로>
```

## 12. 백엔드 자동 전송이 안 되는 문제

### 수동 전송은 성공함

단일 JSON 수동 전송 결과:

```text
status = 201
stored = true
```

### 그런데 자동 전송이 안 되는 이유 후보

`server/api/candidates.py`에 다음 조건이 있음:

```python
if backend_cfg.enabled and should_forward_level(effective_level):
```

`should_forward_level()`은 다음으로 확인됨:

```python
def should_forward_level(level: str | None) -> bool:
    return str(level or "").lower() in {"abnormal", "danger"}
```

즉 자동 전송은 `effective_level`이 다음일 때만 실행됨:

```text
abnormal
danger
```

`normal`, `warning`, `safe`, `info` 등은 전송되지 않음.

### batcher 구조

`server/main.py`:

```python
app.state.backend_event_batcher = BackendEventBatchScheduler(
    BackendForwarder(backend_cfg),
    interval_sec=backend_cfg.batch_interval_sec,
)
app.state.backend_normal_batcher = BackendEventBatchScheduler(
    BackendForwarder(backend_cfg),
    interval_sec=backend_cfg.normal_batch_interval_sec,
)
```

`BackendEventBatchScheduler.submit()`:

```python
self._events.append(event)
if not force and not self._should_flush():
    return BackendBatchSubmitResult(queued=len(self._events))
return self.flush()
```

중요:

```text
이 batcher는 자동 타이머가 아님.
submit()이 호출될 때만 flush 여부를 검사함.
이벤트 1개만 들어오고 이후 새 이벤트가 없으면 interval 시간이 지나도 자동 전송되지 않을 수 있음.
```

### 테스트용 임시 수정

`server/api/candidates.py`에서:

```python
submit_result = batcher.submit(backend_event)
```

임시로 다음처럼 변경하면 즉시 전송 테스트 가능:

```python
submit_result = batcher.submit(backend_event, force=True)
```

## 21. Codex에게 요청할 수정 요약

아래 항목을 우선 반영하도록 요청하면 됨.

```text
1. server/config.orin.yaml의 backend.base_url은 반드시 http:// 포함하도록 검증 또는 자동 보정.
2. BackendForwarder에서 invalid_url 발생 시 로그를 남기도록 수정.
3. candidates.py에 BACKEND_GATE 디버그 로그 추가.
4. BackendEventBatchScheduler.submit/flush에 queue, elapsed, should_flush, response 상태 로그 추가.
5. 테스트 모드에서는 batcher.submit(..., force=True) 옵션을 사용할 수 있게 설정화.
6. skeleton_ws.py에서 persist_pi5_skeleton_batch 실패가 WebSocket을 끊지 않도록 try/except + rollback 처리.
7. skeleton 수신 후 프론트로 broadcast하는 코드가 없으면 프론트용 WebSocket endpoint와 broadcast hub 추가.
8. 파일 업로드는 /clips/upload의 X-API-Key 인증과 CLIP_UPLOAD_API_KEY 환경변수를 명확히 검증하도록 로그 추가.
9. SQLite 엔진에 timeout=30, PRAGMA busy_timeout=30000, WAL, synchronous=NORMAL 적용.
10. 403/467/400/422 같은 non-retryable 응답은 backend_contract_errors.jsonl에 남기고 로그에도 상태코드와 body 앞부분을 출력.
```
