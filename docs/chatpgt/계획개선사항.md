3.2 PatternAnalyzer snapshot/restore — 추가 보완
누락된 항목:
동시 쓰기 경쟁 조건 미처리. 60초마다 atomic write를 하지만, snapshot 저장 중 서버가 SIGTERM을 받으면 파일이 반쪽만 쓰인 상태로 남을 수 있습니다.
권장 구현:
python# atomic write 패턴
tmp_path = snapshot_path.with_suffix('.tmp')
tmp_path.write_text(json.dumps(state))
tmp_path.rename(snapshot_path)  # POSIX에서 원자적
상태 크기 상한 미정의. 장기 운영 시 track 수가 늘어나면 snapshot 크기가 무한히 커집니다. 다음 항목을 추가해야 합니다:

max_track_age_sec: 마지막 activity 후 N초 이상 지난 track은 snapshot에서 제외
max_snapshot_size_kb: 초과 시 경고 + 오래된 track 우선 제거

복원 후 window 연속성 검증 누락. 재시작 후 window_end_ts와 현재 시간 차이가 일정 임계값(예: 300초)을 초과하면 snapshot을 사용하더라도 anomaly vote를 리셋해야 합니다. 그렇지 않으면 300초 공백을 "이상 없음"으로 잘못 판단할 수 있습니다.
추가할 복원 정책:
if (now - snapshot.window_end_ts) > config.max_gap_sec:
    restore skeleton state only (track 목록)
    reset anomaly vote, inactivity timer
    log: "gap too large, partial restore"
테스트 추가:

test_snapshot_atomic_write.py: 쓰기 중 강제 종료 시 이전 snapshot 보존 확인
test_snapshot_large_track_count.py: track 100개 이상 시 size 상한 동작 확인


3.3 운영 백엔드 연동 — 추가 보완
누락된 항목:
clip upload 실패 시 local 보관 정책 미정의. 50MB 초과 또는 S3 PUT 실패 시 clip을 어디에, 얼마나, 어떤 형식으로 보관하는지 정의가 없습니다.
권장 정책:
yamlclip_fallback:
  local_dir: server/storage/clips/pending/
  max_size_gb: 2.0          # 초과 시 오래된 것부터 삭제
  retention_hours: 48       # 48시간 후 자동 삭제
  oversized_action: skip    # skip | resize | split
payload contract 버전 관리 누락. 백엔드 API가 변경될 경우를 대비해 X-API-Contract-Version 헤더를 요청에 포함하거나, payload에 schema_version 필드를 추가해야 합니다. 현재 계약이 바뀌면 4xx가 아닌 silent 오류로 넘어갈 위험이 있습니다.
pending retry 상한 미정의. 네트워크 단절 시 pending queue가 무한히 쌓이는 문제가 있습니다.
추가할 설정:
yamlretry_policy:
  max_pending_events: 10000
  max_pending_age_hours: 24
  backoff_seconds: [5, 30, 120, 600]
  overflow_action: drop_oldest  # 또는 drop_lowest_severity
smoke 테스트 시나리오를 단계별로 세분화:

test_backend_payload_contract.py: mock 서버 대상, payload 필드/타입 검증
test_backend_forwarder_retry.py: 5xx mock 응답에서 retry 동작 검증
tools/test_backend_batch.py: 실 서버 smoke (APP_TOKEN 필요, CI 제외)


3.4 Overlay JSON WS — 추가 보완
누락된 항목:
overlay frame과 WebRTC 영상의 timestamp 동기화 메커니즘이 미완. 현재 "가장 가까운 overlay frame 표시"만 언급되지만, WebRTC는 PTS(Presentation Timestamp) 기반이고 overlay는 시스템 클럭 기반입니다. 이 둘이 drift하면 skeleton이 사람보다 앞서거나 뒤처지게 됩니다.
권장 추가 설계:

overlay JSON에 rtsp_pts_ms 필드 추가 (MediaMTX가 제공하는 경우)
없으면 capture_ts 기준 ±200ms 허용 오차를 명시하고, 초과 시 overlay를 숨기고 stale: true 플래그 전송

WS 연결 끊김 후 재연결 정책 미정의. 프론트가 WS 재연결 시 마지막 sequence_id를 보내면 Orin이 해당 이후 frame만 전송하는 방식, 또는 매번 최신 frame부터 시작하는 방식을 명시해야 합니다.
overlay broadcaster의 메모리 누수 방지. camera_id별 subscriber 목록에서 연결이 끊긴 subscriber를 언제 제거하는지 정의가 없습니다. asyncio.wait_for + 타임아웃 또는 heartbeat ping/pong 기반 정리를 명시해야 합니다.
추가 필드 권장:
json{
  "stale": false,            // overlay가 영상보다 오래된 경우
  "rtsp_pts_ms": 123456,     // 가능한 경우
  "analysis_stage": "stgcn", // "bbox_only" | "action" | "stgcn"
  "drop_count": 0            // 해당 camera_id에서 drop된 frame 수
}

구체화된 실패 조건:
yamlfailure_thresholds:
  edge_process_down_sec: 30         # 30초 이상 응답 없으면 failure
  server_down_sec: 60
